# Code style
- don't assume that the codebase always follows these principles as it might be accumulating tech debt across iterations: never assume that the patterns you see in the codebase are actually those desired by the user. You are here to have opinionated thoughts about the shape of the components in order to reduce, when possible, the cognitive load of the implementations. 
  - during refactoring tasks, if you notice violations of the principles below, you should tell the reader about them, flagging them as bullet points (with minimal text) prepending the 🌿 emoji
- complexity must always have its own reason to exist
- responsibility boundaries of functions and types should be well shaped: if the same responsibility starts being fragmented across different components then it is very easy for the codebase to become sloppy and the design to be not sound.
  - when designing complex features, shape them having a layered architecture in mind (think about the OSI pyramid) and, only if the complexity requires it, consider leveraging the decorator pattern to actually implement it. 
- when the same goal can be reached either via adding new code or by removing the existing one, always prefer the remove-existing-code-path
- keep code comments to a single line maximum 
  - default to none; rationale goes in the reply, not the source
  - stopgaps in a multi-step plan get `// TODO: temporary until <step>.`
  - when a function explicitly computes a non-trivial formula (beyond sums and differences: inversions, square roots, argmins, piecewise functions), the formula goes in its comment. 
- local variables and method names are by themselves 95% of the information the reader absorbs to understand what that piece of logic is doing, so they must not be vague or sloppy. Method names are allowed to be long if needed to have a faithful understanding of what that logic is doing. The name should state what the function accomplishes, at the level of abstraction the caller cares about.
  - for the same reason, don't nest function calls: having a local variable describing the output of an intermediate evaluation is very important for readability and for understanding what is going on. Moreover, nesting function calls causes indentation, which are a footgun for readability.
    - also inside struct literals, `Some(..)`/`Ok(..)`, `return`, `a()?.b()?` chains and each `||`/`&&` operand
    - accessors included: `f(view.width())` binds `let view_width = view.width();` first
  - name booleans so the branch needs no negation: `is_diff_*`, not `!is_same_*`
    - a positive name over a negated query is fine: `let has_sub_key = !rest.is_empty();`
  - ignored pattern values get a name (`_start_index`), never a bare `_`
  - quantities defined in the notes take their symbol spelled out (`gamma_minus_kappa`, `tau_twice`)
  - if you feel that the name of the function is not sufficient to truly describe what (not how) has been doing at the relevant level of abstraction, it might be symptom that the function is doing too much (i.e. unpacking it into two more sound functions) or too little (i.e. inlining it would be more sound)
- functions, structs methods must earn their existence because they are backing a sound responsibility. When they don't, they must be inlined, and this happens very often for shallow methods `fn do_a_and_b(&self){self.do_a(); self.do_b()}` or when they introduce a new level of indirection which has the only effect of obfuscation: this happens often for methods requiring tribal knowledge about where and when they are supposed to be called e.g. `fn do_after_a_but_before_b(&mut self)`
- methods and functions should not be too long, but they should be unpacked into helper methods or structs only if the single-responsibility rules apply and the responsibility is not shallow: imagine that extracting a piece of logic or a bunch of fields as an independent struct always create a level of indirection:
  - this is very bad if the responsibility backed by these components is shallow or is not even a responsibility
  -  this is very good if it is clear that those components belong to a different level of abstraction in the layered architecture, and so it makes sense delegating to them actions about which you know what is the input, what is the output, but you can abstract away without caring about how it is done
- structure modules following the stepdown rule by uncle bob
  - constructors first, then what the caller arrives for, then its callees in call order; accessors last
- write mutation logic as one flat early-return flow: `let-else` for the first case, one named `is_*` local per check with its own return
- optional fields: `new` leaves them `None`, `with_*` sets them
- Functions must not have hidden side-effects if possible. Example: A `checkPassword()` that also initializes a session is lying about what it does.
- Switch statements or runtime-dependent evaluation should be minimized. For example, if you have a type `struct Translator; impl Translator{fn translate(txt:&str){...}}` which abstractly does the same thing just in different flavors, you should leverage on top of polymorphism, delegating the abstract function to a trait implemented by different strategies, in static dispatch paired with type aliases, like `struct Translator<L>{lang:L} impl<L:Language> Translator<L> {fn translate(txt:&str){lang.translate_from(txt)}} trait Language{fn translate_from(txt:&str);} struct Italian; impl Language for Italian {...} type ItalianTranslator = Translator<Italian>; impl ItalianTranslator {fn to_english(txt:&str){...}}`
  - this is valid also for turbofishing, like `sampler.sample::<Uniform>()`
- The rust comment of a component should be the closest as possible to its one-line natural description of what it actually does and why does it earn its existence via `<verb> <object>`.
  - If no honest name can describe what the component does, say it out loud as it might flag shallow responsibility
  - part of (or the whole) name of the component itself should have an exact match with any of the words of the one-line description
  - Break down the one-line description into separate actions at every conjuction and wherever it lists multiple actions. Then, the tests fails if the component is entitled of different responsibility at once
    - However, if the component is an orchestrator, that is a wrapper of individual componets, each well shaped in responsibility and the wrapper simply defines the policy around its delegates (order, timing, lifecycle) without extra responsibility, then the test passes
- Never use eager construction in the error path: always use lazy construction. For example, prefer always `.ok_or_else` to `.ok` or prefer `.with_context` to `.context` etc.
- Keep the number of tests low: each test you add increases quadratically the cognitive load of the reader and so it should be mindfully budgeted and kept low. The only two kind of unit tests allowed, only when the context really needs it because the code is complex enough that is worth to be tested, are:
  - regression testing: guards from breaking an invariant which should always hold. The invariant should be stated in the panic/error message
  - pin down contracts: consider the test as a tiny-main where you instantiate sibling structures helping the user understanding what is the context involving tested struct. The test becomes a mini-story of the behavior of the struct with the sibling components, explaining a dataflow or an expected interaction. Use local variable names in the first place to tell the user what is going on
