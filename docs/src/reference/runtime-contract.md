# Runtime contract

*Version 1. The attribute names are spelled once, in `crates/svugy/src/render/contract.rs` (`RuntimeContract`).*

The renderer (Rust) and the runtime (`crates/svugy/runtime/svugy.js` and `crates/svugy/runtime/svugy.css`) only talk through the `data-svugy-*` attributes in the rendered document. Both profiles emit them, so even a static file stays machine-readable; without script they do nothing. The static profile leaves out the overlays and the animated dots, because it has no entered view and no animation.

Any rename, removal or change of meaning bumps the version. The runtime embedded in a file always matches that file, so the version number is really for outside readers, like a preview tool or an agent parsing rendered SVGs.

Element paths never become an id, a class or a CSS selector. They only travel as attribute values, and the runtime finds elements by comparing `getAttribute()` results, never by building a selector out of a path. The only ids in the document are synthetic ones like `arrowhead-0`, used for `<defs>` references. Detail panels are built from JSON with `textContent` and DOM calls, never `innerHTML`.

The root is `<svg data-svugy-contract="1">`, and its viewBox is the top-level view the runtime returns to. Right after the canvas `<rect>` and the ground grid come the diagram's title and subtitle, then the legend, all in document coordinates and with no data attributes. A click on them counts as a click on empty canvas, and once you enter a level they can fall outside the view. The root level's content is wrapped in `<g data-svugy-level="" data-svugy-view="…">`; the root's path is the empty string and its view equals the SVG's viewBox.

Every solid is a `<g data-svugy-element="PATH">` holding its faces, then its interior level if it has one, then its labels, then its badges. If the element's `link:` resolves to a model path, the group gets `data-svugy-goto="LEVEL"` and a click enters that level instead; a link to a leaf resolves to the leaf's enclosing level. A URL link wraps the group in `<a href="…">` after the link sanitiser, with no data attribute. A container's interior is a `<g data-svugy-level="PATH" data-svugy-view="…" transform="…">` nested inside its solid's group, with the same PATH.

A connection is a `<g data-svugy-edge="EDGE">` holding its stroke, `<path data-svugy-flow="">`, whose dash offset the runtime CSS animates, and in the interactive profile its dot, `<circle data-svugy-dot="">`, moved by SMIL `<animateMotion>` and hidden under reduced motion. A labelled connection gets a second group with the same `data-svugy-edge`, painted after every arc of its level so labels sit on top; both carry the same title and details, and the runtime never assumes edge groups are unique. A badge is an edge group inside its source's element group: a mini of the target, the edge's only group, with no flow path or dot. Clicking it acts like clicking inside its source's level.

Each level group ends with a `<g data-svugy-overlay="">` holding what only the entered view shows; CSS hides it until that level is entered. Inside it, each stub marker is a `<g data-svugy-stub="PATH" data-svugy-goto="LEVEL">`, where PATH is the external endpoint and LEVEL the deepest container holding it (or the endpoint itself, if it's a container).

Every element, edge and stub group starts with `<title>LABEL</title><desc data-svugy-details="">JSON</desc>`. Browsers show the title as a native tooltip even without script. A stub's title is "to " plus the external endpoint's label. The runtime's CSS sits in a `<style>` near the top and its JavaScript in a `<script>` as the root's last child, both in the writer's CDATA form, and the runtime only binds to the SVG it lives in.

Paths are written the way `ElementPath` displays them: dot-separated, with segments quoted when needed, and the empty string for the root. Edges are written the way `EdgeId` displays them: `(FROM -> TO)[ORDINAL]`. `data-svugy-view` is `min-x min-y width height` in document coordinates, with every enclosing frame already applied and fixed decimals; it's the viewBox the runtime animates to when the level is entered.

The details JSON has one object per group, and empty keys are left out. An element is `{"kind":"element","path":…,"label":…,"caption":…,"metadata":{…}}`, an edge is `{"kind":"edge","edge":…,"from":…,"to":…,"label":…}`, and a stub is `{"kind":"stub","target":…,"edges":[edge objects]}`.

Some state belongs to the runtime alone and is never rendered. `data-svugy-entered=""` sits on exactly one level group, the one currently entered, and the CSS keys visibility on it: overlays are hidden, and `[data-svugy-entered] > [data-svugy-overlay]` is visible. It always uses `visibility`, never `display:none`. At start-up the runtime also adds `tabindex`, `role="button"` on groups you can enter, an `aria-label` from each group's title, `tabindex="-1"` on the root SVG, and the `svugy-panel*` classes for the detail panel.

Navigation works like this. Clicking an element enters the outermost container between the current level and that element; clicking a leaf at the current level shows its details instead. If you click something outside the entered level (visible at the edges once zoomed in), the same rule starts from the nearest open level that contains it. Clicking an edge shows its details if it belongs to the entered level, and otherwise acts like a click on its home container. `data-svugy-goto` overrides all of this and enters its level directly. Escape, or a click on empty canvas, goes up one level. Entering animates the viewBox to the level's `data-svugy-view`; with reduced motion it jumps instead.
